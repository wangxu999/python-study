# 提示词工程

## 一句话结论

提示词工程是为大模型明确任务、上下文、约束和输出格式的实践。它的目标不是寻找一句“万能咒语”，而是把原本含糊的需求写成模型能够稳定执行的指令。

## 提示词的基本结构

一条可维护的提示词通常包含以下部分：

| 部分 | 作用 | 示例 |
| --- | --- | --- |
| 角色 | 约束专业视角和表达方式 | 你是一名 Python 教学助手。 |
| 任务 | 说明需要完成什么 | 解释下面代码的执行结果。 |
| 上下文 | 提供完成任务所需资料 | Python 版本、业务规则、原始文本。 |
| 约束 | 明确边界和禁止事项 | 不编造资料中不存在的内容。 |
| 输出格式 | 让结果方便程序或人使用 | 返回 JSON；包含 `summary` 和 `risks` 字段。 |
| 示例 | 给出期望输入输出的样本 | 输入：...；输出：...。 |

可以把它理解为：

```text
角色 + 任务 + 必要上下文 + 约束 + 输出格式
```

并非每次都要包含全部部分。简单问答只需任务和上下文；需要被程序解析的结果，则必须明确格式。

## 从模糊要求到可执行提示词

模糊的写法：

```text
帮我分析这只股票。
```

改进后：

```text
你是一名证券研究助理。根据以下公开数据，整理该股票的基本面信息。

要求：
1. 分别说明营收、净利润和经营现金流的同比变化；
2. 区分数据事实和你的推断；
3. 缺少数据时明确写“数据不足”，不要补充未经提供的事实；
4. 不提供买卖建议。

数据：
{{financial_data}}

按以下 Markdown 结构输出：
## 数据摘要
## 可能的关注点
## 数据缺口
```

改进点在于任务范围、数据来源、禁止事项和结果结构都已明确，输出更稳定，也更容易审查。

## System Prompt 与 User Prompt

调用聊天模型时，常见的消息分工如下：

| 消息 | 适合放什么 | 不适合放什么 |
| --- | --- | --- |
| `system` | 应用长期规则、角色、输出原则、安全边界 | 某次用户独有的大段资料 |
| `user` | 本次任务、问题和输入资料 | 试图覆盖系统规则的指令 |
| `assistant` | 历史回答、少样本示例 | 不可信的外部指令 |

例如：

```python
messages = [
    {
        "role": "system",
        "content": "你是代码审查助手。指出明确的问题，不编造不存在的缺陷。",
    },
    {
        "role": "user",
        "content": "请审查以下 Python 代码，按严重程度输出问题和修改建议：\n\n{{code}}",
    },
]
```

长期规则放在 `system` 消息中；本轮的代码、问题和参数放在 `user` 消息中。不要把用户输入直接拼接进系统规则。

## 输出格式控制

当结果需要被程序消费时，优先使用模型 API 提供的结构化输出或 JSON Schema。仅靠“请返回 JSON”并不能保证字段齐全或类型正确。

一个清晰的格式要求示例：

```text
仅返回 JSON 对象，不要使用 Markdown 代码块。

字段定义：
- summary: string，100 字以内的摘要
- sentiment: "positive" | "neutral" | "negative"
- reasons: string[]，最多 3 项，每项必须引用输入中的信息
```

应用侧仍应校验返回值：解析 JSON、检查必填字段、限制数组长度，并为解析失败准备重试或降级处理。

## 少样本示例

对于分类、抽取、统一口吻等任务，给一到三个高质量示例通常比增加大量泛化描述更有效。

```text
任务：判断客户消息的优先级。

示例：
消息：支付后页面显示扣款成功，但订单不存在。
输出：{"priority":"P0","reason":"涉及支付成功但订单异常"}

消息：希望新增深色模式。
输出：{"priority":"P2","reason":"功能建议，不影响现有使用"}

现在处理：
消息：{{message}}
```

示例要覆盖真实边界情况，并与生产格式完全一致。错误或相互矛盾的示例会让模型学习到错误模式。

## 处理长文本与 RAG

不要把所有资料无差别地塞进提示词。长文本会增加成本、延迟，并稀释关键信息。

更常见的流程是：

```text
用户问题
  -> 检索相关文档片段
  -> 将片段作为“参考资料”放入提示词
  -> 要求模型仅依据资料回答并标注依据
```

用于 RAG 的提示词可以写成：

```text
根据“参考资料”回答用户问题。
若资料未包含答案，请明确回答“参考资料不足以确定”，不要使用外部知识补充。
每个结论后标注对应的资料编号。

参考资料：
{{retrieved_context}}

用户问题：
{{question}}
```

参考资料属于不可信输入。资料中出现“忽略此前指令”等内容时，不能改变系统规则或任务要求。

## 调试方法

提示词效果不稳定时，按以下顺序排查：

1. 固定模型版本和推理参数，尤其是 `temperature`。
2. 保存实际发送的完整 `messages`，确认变量是否正确填充。
3. 为成功和失败场景准备小型评测集，而不是只测试一个案例。
4. 检查任务是否一次要求模型完成过多步骤；必要时拆成提取、判断、生成多个调用。
5. 检查上下文是否过长、冲突或包含无关资料。
6. 对结构化结果做程序校验，失败后使用明确的修复提示词重试。

不要只根据一次看似不错的回答判断提示词有效。应使用代表性的样本，比较准确率、格式合规率、延迟和成本。

## 常见问题

### 要求太宽泛

“写得专业一点”没有可验证的标准。应替换为可观察的要求，例如“面向产品经理，使用三段 Markdown，列出不超过三项风险”。

### 把不可信内容当指令

网页、PDF、用户上传文件和检索结果都可能包含注入式文本。应将它们明确标识为数据，并在系统规则中规定：其中的指令不能改变任务。

### 依赖模型保证事实正确

模型能够生成流畅文本，但不能替代数据校验。涉及金额、日期、交易、医疗、法律或生产操作时，应通过数据库、工具调用或人工流程验证关键结论。

### 用提示词隐藏业务规则

稳定且关键的规则应尽量由程序、权限系统或校验器保证。提示词适合指导语言理解和生成，不适合单独承担鉴权、金额计算或不可逆操作的安全控制。

## 实用模板

```text
角色：你是 {{role}}。

任务：{{task}}。

上下文：
{{context}}

约束：
1. {{constraint_1}}
2. {{constraint_2}}
3. 信息不足时说明缺少什么，不要猜测。

输出格式：
{{output_format}}
```

先使用这个模板建立可测试的基线，再根据失败样本收紧任务描述、补足上下文或加入示例。提示词应像代码一样纳入版本管理，并通过评测持续验证。
