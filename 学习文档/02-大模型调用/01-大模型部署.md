# 大模型部署

## 一句话结论

大模型部署是把模型权重、推理运行时和对外接口运行在本机或服务器上，使应用能够通过命令行或 HTTP API 调用模型生成结果。学习阶段可先用 Ollama 在本机运行；需要多人、高并发或更高性能时，再使用 Linux 服务器、GPU 和 vLLM 等推理服务。

## 部署与训练的区别

| 概念 | 主要目的 | 是否需要大量训练数据 | 常见资源需求 |
| --- | --- | --- | --- |
| 训练 / 微调 | 让模型学习新能力或特定知识 | 通常需要 | 很高，常需多张 GPU |
| 部署 / 推理 | 使用已训练好的模型生成回答 | 不需要 | 与模型大小、量化、并发有关 |

本笔记讨论的是部署和推理，不是从零训练模型。

## 一个完整部署包含什么

```text
用户 / 前端 / Python 程序
          |
          | HTTP 请求
          v
    大模型服务（Ollama / vLLM）
          |
          v
模型权重 + 推理引擎 + CPU / GPU 显存
```

如果应用需要基于企业文档回答问题，还会增加检索服务和向量数据库，这属于 RAG 应用架构：

```text
用户问题 -> 应用服务 -> 检索相关文档 -> 大模型生成回答 -> 返回结果
```

## 常见部署方式对比

| 方式 | 模型运行位置 | 优点 | 注意点 | 适合场景 |
| --- | --- | --- | --- | --- |
| 云端 API | 模型提供商服务器 | 无需管理 GPU，上手快 | 有调用成本，数据会离开本机或内网 | 原型验证、轻量应用 |
| 本地部署 | 自己的电脑 | 数据可留在本机，开发方便 | 受本机 CPU、内存、GPU 限制 | 学习、个人工具、离线场景 |
| 内网服务器部署 | 公司或团队服务器 | 统一提供模型接口，数据可留内网 | 需要运维、鉴权、监控 | 团队内部应用 |
| 云 GPU 服务器部署 | 云厂商 GPU 实例 | 可按需求扩容，性能较强 | GPU 成本、网络和安全配置 | 对外服务、较高并发 |

学习阶段建议顺序：先用云端 API 理解调用流程，或用本地 Ollama 理解模型运行；确认需求后再研究服务器部署。

## 关键术语

| 术语 | 含义 |
| --- | --- |
| 模型参数量 | 模型规模的常用指标，如 7B、14B、32B；`B` 表示十亿（billion）参数 |
| 推理（inference） | 将提示词发送给已训练模型并得到输出的过程 |
| 模型权重 | 模型训练得到的文件，部署时需要下载或挂载 |
| 量化（quantization） | 用更少位数保存权重，以降低内存 / 显存占用；常见如 4-bit、8-bit |
| 上下文窗口（context window） | 一次请求中模型可处理的输入和输出总长度上限 |
| Token | 模型处理文本的基本单位，不等同于一个汉字或一个英文单词 |
| 并发 | 同一时间处理多个请求的能力 |
| 显存（VRAM） | GPU 上可供模型使用的内存；不足时容易加载失败或变慢 |

## 模型与硬件的基本判断

模型能否运行不仅取决于参数量，还受量化方式、上下文长度、并发数和推理框架影响。下表只是保守的学习阶段参考，实际以运行时提示为准。

| 模型规模 | 常见学习用途 | 本地运行的建议资源 | 说明 |
| --- | --- | --- | --- |
| 1B - 4B | 基础测试、轻量任务 | 8GB 以上系统内存 | CPU 也可运行，质量和速度有限 |
| 7B - 8B | 日常对话、简单代码辅助 | 16GB 以上系统内存；有 8GB 以上显存更好 | 本地学习常用选择 |
| 14B - 16B | 更复杂的问答、代码任务 | 32GB 以上系统内存；有 16GB 以上显存更好 | CPU 推理可能较慢 |
| 32B 及以上 | 更高质量、复杂任务 | 通常建议大显存 GPU 或服务器 | 本地普通电脑往往不适合 |

量化后的模型占用通常显著更低，但模型加载后还会占用运行时内存、KV Cache 等空间。不要只按模型文件大小判断是否能运行。

## 本地部署入门：Ollama

Ollama 是本地运行大模型的常用工具。它负责下载、管理和运行模型，并提供本机 HTTP API。Windows 可以从 [Ollama 官网](https://ollama.com/) 下载对应安装程序。

### 1. 检查安装

安装完成后，在 PowerShell 或 PyCharm 终端执行：

```powershell
ollama --version
```

能看到版本信息说明命令可用。若提示找不到 `ollama`，可重开终端；仍无效时检查是否已正确安装并加入环境变量。

### 2. 下载并运行模型

以一个 8B 量级模型为例：

```powershell
ollama run qwen3:8b
```

首次执行会下载模型，完成后进入对话。输入问题后按回车即可生成回答；输入 `/bye` 退出对话。

也可以先只下载，再单独启动：

```powershell
ollama pull qwen3:8b
ollama run qwen3:8b
```

常用管理命令：

```powershell
ollama list          # 查看已下载模型
ollama ps            # 查看当前正在运行的模型
ollama rm qwen3:8b   # 删除本地模型，释放磁盘空间
```

模型名称和可用标签会随模型仓库更新；实际使用前请以 Ollama 模型库中的名称为准。

### 3. 用 HTTP API 调用本地模型

Ollama 默认在本机提供服务，常用地址为 `http://localhost:11434`。下面示例使用 Python 的 `requests` 发送一次对话请求。

先安装依赖：

```powershell
py -m pip install requests
```

Python 示例：

```python
import requests

url = "http://localhost:11434/api/chat"
payload = {
    "model": "qwen3:8b",
    "messages": [
        {"role": "user", "content": "用三句话解释什么是 Python 模块"},
    ],
    "stream": False,
}

response = requests.post(url, json=payload, timeout=120)
response.raise_for_status()

data = response.json()
print(data["message"]["content"])
```

`stream=False` 表示等待完整回答后一次返回，便于初学时处理 JSON。流式输出时，服务会分段返回内容，前端聊天界面通常会使用这种方式实现逐字显示效果。

### 4. 处理连接失败

如果 Python 调用时报“连接被拒绝”，先确认：

```powershell
ollama ps
```

并确认 Ollama 服务正在运行。某些安装方式会自动启动本地服务；如果没有，可根据当前安装版本的官方文档启动服务。不要在不了解网络配置时直接把本机 `11434` 端口暴露到公网。

## 生产部署：服务化推理

Ollama 很适合本地开发、测试和个人使用。生产环境更常见的方式是在 Linux + NVIDIA GPU 服务器上使用专门的推理服务，例如 vLLM、TensorRT-LLM 或云厂商模型服务。

典型架构：

```text
客户端
  |
  v
业务后端（鉴权、限流、业务逻辑、日志）
  |
  v
模型服务（vLLM 等，管理 GPU 与模型）
  |
  v
模型权重 / GPU
```

业务后端不应把模型服务端口直接裸露给所有用户。通常由后端统一进行：

- 身份认证和权限校验。
- 请求限流，防止单个用户耗尽 GPU。
- 提示词组装、会话历史裁剪和敏感信息处理。
- 超时、重试和降级策略。
- 调用日志、耗时、Token 使用量和错误监控。

### 为什么生产环境常用 vLLM

vLLM 是面向高吞吐推理的服务框架，常用于 GPU 服务器场景。它的优势通常包括批处理调度、显存管理和与 OpenAI 风格 API 的兼容能力。

是否使用 vLLM 取决于实际需求：只有个人本地测试时，Ollama 往往更简单；需要多个用户共享 GPU、处理并发请求时，vLLM 更合适。

## 部署前检查清单

- [ ] 明确任务：对话、代码辅助、文档问答，还是结构化信息提取？
- [ ] 明确模型许可证是否允许当前用途，尤其是商业使用。
- [ ] 确认模型大小、量化方式与机器内存 / 显存是否匹配。
- [ ] 确认上下文长度和预期并发，避免 KV Cache 占满显存。
- [ ] 先用固定测试问题评估回答质量、响应时间和资源占用。
- [ ] 设置请求超时、错误提示、日志和监控。
- [ ] 对外服务时设置鉴权、限流和网络访问控制。
- [ ] 不把密钥、用户隐私数据或内部文档直接写进代码和日志。

## 常见问题

| 现象 | 可能原因 | 排查方向 |
| --- | --- | --- |
| 模型下载很慢或失败 | 网络、镜像源、磁盘空间不足 | 检查网络、剩余磁盘空间和工具提示 |
| 模型无法加载 | 内存 / 显存不足，模型过大 | 换更小模型或更低量化版本，关闭其他占资源程序 |
| 第一次回答很慢 | 模型首次加载到内存或显存 | 再发送一次请求，观察后续响应时间 |
| CPU 占用很高、生成很慢 | 未使用 GPU 或硬件性能有限 | 检查运行时硬件支持，考虑小模型或 GPU |
| Python 连接被拒绝 | 本地服务未启动、端口不正确 | 检查服务状态和请求 URL |
| 回答被截断 | `max_tokens` 设置过小或上下文窗口不足 | 调整输出限制，裁剪历史消息或选择更大上下文模型 |
| 多人使用后变慢 | 并发超出机器能力 | 限流、排队、增加 GPU 或使用高吞吐推理服务 |

## 易错点

- [ ] 把“部署模型”理解为“训练模型”。
  - 正确做法：部署通常是加载现成模型做推理，不需要重新训练。
- [ ] 只看模型参数量，不看量化、上下文长度和并发。
  - 正确做法：这些因素都会影响内存 / 显存占用和速度。
- [ ] 直接将本地 Ollama 端口开放到公网。
  - 正确做法：生产服务应放在受控网络后，并通过应用后端做鉴权和限流。
- [ ] 在程序中硬编码模型 API 密钥。
  - 正确做法：使用环境变量或专门的密钥管理方式。
- [ ] 将模型回答当作绝对正确结果。
  - 正确做法：对关键业务增加校验、人工审核或规则兜底。
- [ ] 只在单次请求正常时就上线。
  - 正确做法：还要测试长文本、异常输入、并发、超时和资源耗尽场景。
