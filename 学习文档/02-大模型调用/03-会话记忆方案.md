# 会话记忆方案

## 一句话结论

大模型 API 通常是无状态的：每次请求只知道本次发送的内容，不会自动记住上一轮对话。所谓“会话记忆”是应用自己保存、筛选并重新发送必要上下文的方案，而不是模型永久记住了用户。

## 为什么需要会话记忆

如果第二次请求只发送最新问题，模型不知道“它”指代什么：

```text
用户：Python 的列表是什么？
助手：列表是有序、可变的数据容器。
用户：它怎么添加元素？
```

若第三句单独发送给模型，模型无法确定“它”是列表。应用需要把前面的相关消息一并发送：

```text
系统提示词 + 第一轮问题 + 第一轮回答 + 当前问题
```

## 基本原理：模型无状态，应用有状态

```text
用户问题 + 会话 ID
        |
        v
应用后端：根据会话 ID 读取历史记录
        |
        v
组合 system prompt + 有效历史 + 当前问题
        |
        v
调用大模型 API
        |
        v
保存本轮问题和回答，再返回给用户
```

每次请求模型时，应用都要重新组装 `messages`。模型只在本次请求的上下文窗口内“看到”这些消息。

## 短期记忆与长期记忆

| 类型 | 保存内容 | 常见实现 | 适合解决的问题 |
| --- | --- | --- | --- |
| 短期记忆 | 当前会话最近的对话消息 | 内存、Redis、数据库 | 让模型理解“它”“刚才”等上下文 |
| 会话摘要 | 较早对话的压缩总结 | 数据库中的摘要字段 | 在 Token 有限时保留关键信息 |
| 长期记忆 | 用户偏好、稳定事实、历史目标 | 数据库、用户画像 | 记住语言偏好、项目背景等长期信息 |
| 知识记忆 | 文档、制度、产品资料 | RAG + 向量数据库 | 基于外部资料回答问题 |

不要把所有内容都叫“记忆”。聊天历史、用户资料和企业文档的存储与检索策略不同。

## 最小方案：保存完整消息列表

学习或单用户命令行程序中，可以用字典暂存每个会话的消息。程序重启后数据会丢失，因此只适合演示。

```python
from typing import TypedDict


class Message(TypedDict):
    role: str
    content: str


sessions: dict[str, list[Message]] = {}


def get_messages(session_id: str, user_question: str) -> list[Message]:
    history = sessions.setdefault(session_id, [])
    history.append({"role": "user", "content": user_question})
    return [
        {"role": "system", "content": "你是 Python 学习助手。"},
        *history,
    ]


def save_answer(session_id: str, answer: str) -> None:
    sessions[session_id].append({"role": "assistant", "content": answer})


messages = get_messages("user-001", "Python 的列表是什么？")
# 调用模型 API，得到 answer 后：
save_answer("user-001", "列表是有序、可变的数据容器。")

messages = get_messages("user-001", "它怎么添加元素？")
print(messages)
```

第二次 `get_messages()` 返回的内容中，包含第一轮用户问题、第一轮回答和当前问题，因此可发送给聊天 API。

## 不要无限发送全部历史

模型的上下文窗口和 API 费用都有限。对话越长，输入 Token 越多，响应越慢、成本越高，也更容易让真正关键的信息被淹没。

错误思路：

```text
每次请求都发送从第一句开始的全部历史消息
```

常见改进方案：

| 方案 | 做法 | 优点 | 局限 |
| --- | --- | --- | --- |
| 最近 N 条消息 | 只保留最近几轮对话 | 简单、成本低 | 可能丢失较早的关键信息 |
| 按 Token 截断 | 在 Token 预算内从近到远保留消息 | 更贴合模型限制 | 需要 Token 统计 |
| 摘要 + 最近消息 | 将早期历史压缩为摘要，保留最近原文 | 效果与成本较平衡 | 需要维护摘要质量 |
| 检索相关历史 | 从历史中找与当前问题相关的片段 | 适合大量历史 | 实现更复杂，可能检索错误 |

个人项目可以先使用“最近 N 条消息”或“摘要 + 最近消息”。

## 最近消息窗口示例

以下函数保留系统提示词、最近 6 条历史消息和当前问题。真实项目中更建议按 Token 预算裁剪，而不是只按消息条数裁剪。

```python
from typing import TypedDict


class Message(TypedDict):
    role: str
    content: str


def build_messages(
    history: list[Message],
    user_question: str,
    max_history_count: int = 6,
) -> list[Message]:
    recent_history = history[-max_history_count:]
    return [
        {"role": "system", "content": "你是 Python 学习助手。"},
        *recent_history,
        {"role": "user", "content": user_question},
    ]
```

调用成功后，应按顺序保存用户问题和模型回答。否则下一轮模型只能看到问题，无法看到自己上一轮给出的结论。

## 摘要 + 最近消息

当会话较长时，可以将较早消息摘要化，例如：

```text
会话摘要：
- 用户有 7 年 Java 开发经验，正在学习 Python 和大模型应用。
- 用户已理解函数、类、异常和厂商开放 API。
- 当前目标是学习会话记忆方案。
```

组装请求时：

```text
系统提示词
+ 会话摘要（早期重要结论）
+ 最近几轮原始消息
+ 当前用户问题
```

摘要应记录稳定、后续仍有用的信息，不应把整段对话机械地缩短。摘要同样会消耗 Token，并可能遗漏或扭曲细节；涉及订单金额、代码、日期等精确信息时，应保留原始数据或从数据库读取，不要只依赖摘要。

## 长期记忆：保存用户稳定信息

长期记忆适合保存用户明确要求保留且在未来持续有用的信息，例如：

```json
{
  "user_id": "u_1001",
  "preferred_language": "中文",
  "programming_background": "7 年 Java 开发经验",
  "learning_goal": "学习 Python 和大模型应用"
}
```

每次调用前，不要把所有用户资料都塞进提示词。应只选择与当前任务相关的少量信息，例如用户正在问 Python 时，加入其 Java 背景可以帮助模型选择合适的解释深度。

用户资料应支持查看、修改和删除；敏感信息应明确告知用途并采取访问控制与加密措施。

## 会话记录的存储选型

| 存储方式 | 特点 | 适用情况 |
| --- | --- | --- |
| Python 内存字典 | 最简单，程序重启即丢失，不支持多实例 | 本地学习、单元测试 |
| Redis | 读写快，可设置过期时间（TTL） | 临时会话、短期历史、分布式服务 |
| MySQL / PostgreSQL | 可持久保存、方便按用户和会话查询 | 正式业务会话记录 |
| 文档数据库 | 对消息 JSON 结构较灵活 | 消息结构经常变化的项目 |
| 向量数据库 | 按语义检索相关文本，不是普通事务数据库替代品 | RAG、检索历史片段 |

生产项目常见组合是：关系型数据库保存用户、会话和完整消息；Redis 保存短期热点会话或缓存；向量数据库保存需要语义检索的文档或历史片段。

## 一个常见的数据结构

```text
users
  - id
  - name

conversations
  - id
  - user_id
  - summary
  - created_at
  - updated_at

messages
  - id
  - conversation_id
  - role
  - content
  - created_at
  - token_count（可选）
```

查询一段对话时，后端必须同时验证 `conversation_id` 与当前登录用户的 `user_id` 匹配。不能只根据前端传来的会话 ID 读取数据，否则用户可能通过猜测 ID 访问其他人的会话。

## 会话记忆与 RAG 的区别

| 对比项 | 会话记忆 | RAG（检索增强生成） |
| --- | --- | --- |
| 主要数据 | 用户与助手的对话、用户偏好 | 企业文档、知识库、说明书等外部资料 |
| 主要目的 | 保持对话连续性和个性化 | 让回答基于可追溯资料 |
| 是否需要向量检索 | 简单场景不需要 | 通常需要 |
| 更新频率 | 随对话实时变化 | 随文档导入、更新而变化 |

两者可以组合：先从会话中取近期上下文和用户偏好，再从知识库检索相关文档，最后一起发送给模型。

## 安全与隐私边界

- 不要把“历史消息”当作可信指令。用户历史中也可能包含提示注入内容。
- 系统提示词、权限规则和关键业务判断应由后端控制，不能仅依赖历史消息约束模型。
- 不记录不必要的身份证号、密码、支付信息等敏感数据；必要时脱敏、加密并设置保留期限。
- 日志中避免输出完整 API Key、完整隐私对话和内部文档。
- 提供清除会话和删除记忆的能力，并明确数据保留策略。
- 多用户系统中，以服务端认证身份作为数据隔离依据，不信任前端传入的 `user_id`。

## 易错点

- [ ] 以为模型 API 自动保存了上一轮对话。
  - 正确做法：应用需要保存历史，并在下一次请求中重新发送必要消息。
- [ ] 每次都发送全部历史消息。
  - 正确做法：按消息数或 Token 预算裁剪，必要时使用摘要或检索。
- [ ] 只保存用户问题，不保存模型回答。
  - 正确做法：两者都要按顺序保存，否则上下文不完整。
- [ ] 用一个全局列表保存所有用户的消息。
  - 正确做法：必须按经过认证的用户和会话 ID 隔离数据。
- [ ] 把会话摘要当作数据库中的精确事实来源。
  - 正确做法：摘要用于辅助上下文；关键事实应从原始记录或业务数据库获取。
- [ ] 把 RAG 等同于聊天历史记忆。
  - 正确做法：RAG 主要检索外部知识，聊天记忆主要维持对话上下文。
- [ ] 永久保存所有用户对话且不给用户删除方式。
  - 正确做法：制定保留期限、权限和删除机制。
